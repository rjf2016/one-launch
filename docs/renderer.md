# Renderer

React 19 + TypeScript in `src/renderer/src`, built by electron-vite. It is sandboxed with no Node access. The only way out is `window.oneLaunch.invoke`, reached through `lib/ipc.ts`. See `architecture.md` for the bridge and IPC, `switching.md` for the job state machine, and `development.md` for the renderer test harness.

## Aesthetic and principles

- Dark only (`color-scheme: dark`), premium game launcher, not an admin tool. Artwork-forward: the Library is a poster wall.
- Motion is subtle: `transition-colors duration-150` on interactive elements, 200 ms `ease-out` for the sidebar width. No bouncy or layout-shifting animation. Add `motion-reduce:transition-none` to anything that moves. The setup guide and the What's New card are the only places with entrance fades, and the guide has two slow loops (below); all of it is opacity and transform, and none of it runs under reduced motion.
- Light deps only: Tailwind 4 (CSS-first config in `index.css`), `lucide-react` icons, `zustand`. No component, animation, chart or router library. Don't add one.
- Native `<select>` is banned: its OS-drawn popup cannot be themed. Use `Dropdown` (selection) or `MenuButton` (actions).
- Layout must hold from the 960 px minimum window width to fullscreen: no horizontal page scroll, no wrapping button labels (`Button` is `whitespace-nowrap`), no content shift when async text changes length (fixed widths + `truncate`, skeleton rows the same height as the real ones).
- A `Row` hint or `Panel` description is one line at 960 px with the sidebar held open (a 672 px panel, 632 inside): about 100 characters beside a toggle, 75 beside a dropdown, 50 beside the 224 px key field, and for a description whatever the header's buttons leave. `views.mjs` fails on one that wraps. A `Panel` centres its actions on the title and description; a `Row` centres its control on the label and hint.

## Design tokens (`src/renderer/src/index.css`)

- Colours are CSS variables on `:root`, exposed as Tailwind utilities through `@theme inline` (surfaces, text greys, violet `accent`, the status tones, and one colour per launcher). Use the tokens, never raw hex.
- `faint` and `muted` are tuned to at least 4.5:1 on `bg`, `surface` and `surface-2`. Don't put faint text on `surface-3` or darken these tokens.
- Tone pattern for callouts: `border-<tone>/30 bg-<tone>/10 text-<tone>` (warning = needs the user, danger = failed, accent-soft = in progress, success = done).
- Fonts are Segoe UI (`font-sans`, base 14 px) and Cascadia (`font-mono`) for ids and paths. `text-xs` is for hints and `text-sm` for body text. Cards and dialogs use `rounded-panel` with `shadow-panel`.
- `body` is `user-select: none`; inputs opt back in. Add `select-text` to values the user may want to copy (paths, step detail).
- Scrollbars are custom `::-webkit-scrollbar`. The thumb shows only on the container under the pointer via the `.sb-hover` class from `lib/scrollbarHover.ts`. CSS `:hover` does not work: Chromium doesn't repaint custom scrollbars on a host hover change. `.sb-always` keeps the thumb visible regardless, for a list inside a card where nothing else says there is more below (the What's New card).

## Shell and navigation

- There is no router: `view` and `accountRoute` in the store select the page. `App.tsx` mounts the global hosts (`ConfirmDialog`, `RecoveryHost`, `SetupGuideHost`, `WhatsNewHost`, `LaunchHost`) above the views.
- `TitleBar` is a 36 px (`h-9`) drag strip. Main draws the Windows caption buttons over its right end (`titleBarOverlay`). Put nothing interactive in it. Every modal backdrop starts at `top-9` so the window stays draggable. When `app:info` reports `platformSource: 'fake'` it shows a "Fake launchers" `role="status"` badge, so no screenshot of a fake-launcher run can pass for a real one.
- `Sidebar` collapses to icons below 1100 px (`SIDEBAR_NARROW_QUERY`). A manual toggle (Ctrl+B) is stored in `localStorage` until the window crosses the breakpoint. Only the aside width animates. Labels fade in place so nothing reflows. The "Preview mode is on" card shows only when `dryRun === 'true'` and opens Settings on its Advanced tab (`openSettings('advanced')`).
- `Page` scrolls the whole pane. Its `narrow` prop caps forms at 65 rem, and the Library stays full width. `PageHeader` is sticky.
- Global shortcuts go through `isShortcut` (`lib/shortcuts.ts`): none fires while a modal dialog (`aria-modal`) is up, and Ctrl+1/2/3 and Ctrl+B are also skipped while focus is in an input/textarea/contentEditable. Ctrl+F (Library search) and Ctrl+S (save on an account's edit page; the create form has only Create account) fire from fields. The Back gesture (`isBack`: the mouse's Back button, `MouseEvent.button` 3 on `mouseup`, or Alt+Left, which some mouse drivers send instead) leaves an account's page for the Accounts list through `backToAccounts`, so the leave guard still asks; nowhere else has anywhere to go back to, so it does nothing there. The page's own Accounts control is the same ghost button the setup guide uses for Back.

## Store and data flow (`store/ui.ts`, zustand)

- UI state only. Domain data is never cached in the store, with two exceptions: `launcherStatus`, the last `launchers:status` answer, shown at once on later visits while a fresh one loads; and `updateStatus`, the last `updates:status` answer, shared by the sidebar card and Settings › Updates.
- Views fetch with `useIpcQuery(fetcher, deps, seed?)` from `lib/ipc.ts`: `{ data, error, loading, reload }`. It drops stale responses, keeps `data` across reloads (no flash to empty) and clears `error` when a run starts. `seed` is read once, at mount: a startup answer that is already in becomes the first render's data and the first fetch is skipped.
- Startup (`boot.ts`, the first import of `main.tsx`, and `lib/startup.ts`): the preload sends `STARTUP_REQUESTS` the moment the document starts; `prefetchStartup` gathers those answers and `main.tsx` renders once they are in or after 50 ms, whichever comes first, so the first commit already holds the library, the Recent strip, the sidebar's settings and a pending recovery question. While the startup window is open, `peekStartup(channel, req)` serves a settled answer to a mount initialiser and `ipc.invoke` joins a startup call for the same channel and request instead of asking main again; `App`'s first effect closes the window (`closeStartup`), after which every mount and every `reload()` fetches fresh. Read the window only in `useState` initialisers, never in a render body, so a later mount can never show a stale seed.
- `ipc.invoke` throws `IpcError(code, message)`. Show `message`. Branch only on `code`, never on message text.
- `settingsRevision` / `settingsChanged()`: bump it after any `settings:set` so the Sidebar card and the Settings view re-read `settings:getAll`.
- `settingsTab` is the Settings tab in view, kept for the session: `setView('settings')` and Ctrl+3 leave it alone. `openSettings(tab)` lands on one from anywhere (the sidebar's Preview mode card, the Library's artwork-key link); it goes through `navigate`, not `setView`, which returns early while Settings is already up.
- Navigation (`setView`, `openAccount`, `newAccount`, `importAccounts`, `backToAccounts`) goes through `navigate`, which awaits `leaveGuard` (set by account forms while dirty, or while a typed password is not yet stored) and clears the guard on success. `setView('accounts')` from a detail page returns to the list.
- `returnTo` is the game whose Play found no account for its launcher. The launch dialog's empty state leaves through `newAccount(launcher, game)` (Epic, Riot) or `importAccounts(launcher, game)` (Steam, Battle.net), which carry the game through that one navigation; `navigate` drops it on the next. The create form, or an import on the Accounts page, then reopens that game's launch dialog with the new account picked (`openLaunch`). `importIntent` makes the Accounts page open the launcher's import dialog on arrival and clear it.
- `ask(opts)` opens `ConfirmDialog`. If a question is already open it answers `false` straight away.
- Main never pushes to the renderer, so background changes arrive by polling. The Library polls `artwork:status` and reloads when `status.revision` differs from the `revision` its list came with (`library:list` returns both): the startup answer predates the first poll, and on a slow start the startup scan too, so a revision the poll merely saw earlier is not enough. `useUpdateStatus(idleMs)` (`lib/updates.ts`) polls `updates:status` into the store: every second while a check or download runs, else every 60 s from the sidebar and 5 s from Settings. Polling does not back off while the window is hidden.
- Per-viewer UI prefs go in `localStorage` inside try/catch (`sidebar`, `library.sort`). Everything else is a setting in main.

## Launch flow hosting (`components/LaunchHost.tsx`, `LaunchDialog.tsx`)

- `LaunchHost` mounts the dialog above all views. Views only call `openLaunch({ game, initialAccountId })`, and `game: null` means a plain account switch.
- `launchRequest` (the dialog is open) and `activeLaunch` (the job) are separate. The job outlives both the dialog and navigation.
- `LaunchHost` polls `launch:status` every 150 ms while the job is `running`, dialog open or not (an in-memory snapshot over IPC, so the phase list keeps up with the adapter). While the dialog is closed it shows a banner with Show and Dismiss. A `done` banner clears itself after 8 s. Other outcomes stay until dismissed.
- On mount the dialog attaches to a running job, or to a finished job for the same game, and clears any other.
- Escape, the backdrop and X do nothing while the dialog is checking, running or submitting. `submittingRef` blocks a double `launch:start`. A `CONFIRM_REQUIRED` error re-runs the preflight and shows the confirm stage. This is the renderer's only branch on an error code.
- One screen says one thing. The confirm and preview stages show the close box (`closeMessage` plus "is then started again as") once; the preflight's plan arrives without the adapter's own "is running… It will be closed" warning (`withoutCloseWarning` in `src/main/launchers/types.ts`), which the Switch preview on the account page keeps.
- While a job runs the footer offers Stop (`launch:cancel`) and Hide. Stop is left out while the sign-in panel shows, because its Stop waiting does the same; the two share one "Stopping…" state until the job ends.
- Progress is shown as five plain phases from `lib/phases.ts`, with the raw steps behind "Show details". Keep `lib/phases.ts` and `lib/recovery.ts` pure, because they are unit-tested.
- `RecoveryHost` asks once at startup about an interrupted switch. It cannot be dismissed with Escape or the backdrop.

## Setup guide (`components/SetupGuide.tsx`, `SetupGuideSteps.tsx`, `SetupGuideArt.tsx`)

- `SetupGuideHost` asks once at startup and opens the guide for a data folder nobody has set up: `firstRun.dismissed` unset and no account. Settings › General › "Show again" opens it for anyone (`openSetupGuide('settings')` in the store). It is a modal dialog (`z-40`, under the recovery and confirm dialogs), so no shortcut fires behind it, and its backdrop is inert.
- Five steps: Welcome; Your launchers (`launchers:status`, Locate… on each missing row, the installed-game count polled from `artwork:status` and `library:list`, and the artwork sentence); How Play works (three points and a self-playing phase list built from `lib/phases.ts`); Your accounts (what Steam and Battle.net remember, in one import across both, one line naming any installed launcher that keeps no list, plus "Add by hand" toggles); Ready (the summary). The footer navigates (Back, Skip, Continue) and actions live in the step body, with one exception: on the accounts step, while ticked rows are not yet imported, the primary reads "Import n and continue" and imports them before moving on, so a ticked list never ends the guide with nothing (a failed import stays on the step).
- Every way out writes `firstRun.dismissed` and closes: Skip, Escape, the X, Open Library, Go to Accounts, and "Add a <launcher> account", which opens that launcher's new-account form. A save that fails still closes the guide; it comes back next start. The guide never opens by itself once dismissed or once an account exists, so installs that predate it never see it.
- Each step opens with the focus on its primary action, an sr-only `role="status"` announces "Step n of 5: <name>", and the dialog is named by the step heading (`id="setup-title"`).
- Motion: the card and each step fade in (`guide-card`, `guide-fwd` / `guide-back`), rows rise with a stagger (`guide-rise` plus an inline `animationDelay`), check marks pop, the welcome art swaps the account name on a 5 s loop and rings the Play button, and the phase demo advances on a JS clock (`useLoop`, `lib/motion.ts`). `usePrefersReducedMotion` freezes the loops and the CSS block turns the rest off. A screenshot taken the instant a step mounts catches the entrance mid-fade; scenarios settle for 900 ms first.

## What's New (`components/WhatsNewDialog.tsx`)

- The notes live in `src/shared/whats-new-releases.ts`, newest first: a version, a `YYYY-MM-DD` date, an optional intro sentence, an optional `image` (a file in `src/renderer/src/assets/whats-new/`, bundled by `import.meta.glob` in `lib/whatsNewImages.ts` and shown full width at the top of the list), and `sections`, each a `heading` in one of `WHATS_NEW_TONES` (`accent` by default, the status tones, or a launcher colour) over its `items`, changes with a bold `lead` and a plain `detail`. An entry announces itself once, and the same entry is the GitHub release's notes (`scripts/release-notes.mjs`, run by the release workflow), so every release has one. `test/whats-new.test.ts` refuses a malformed entry, a missing image file, a section with no changes, or an entry newer than `package.json`.
- Development builds only: the Advanced tab of Settings ends with a Developer panel (`components/WhatsNewDevPanel.tsx`, loaded lazily behind `import.meta.env.DEV`, so a production bundle never contains it) whose "Preview What's New" opens any entry in the file, whatever the running version. Under `npm run dev`, saving the file updates the open card (`import.meta.hot.accept` on the releases module swaps the store's release for the new one).
- `WhatsNewHost` asks once at startup (`settings:getAll`, `app:info`, `recovery:get`) and opens the card about 400 ms later, over the painted Library, when `pickWhatsNew` (`src/shared/whats-new.ts`) finds an entry at or below the running version and newer than `whatsNew.lastSeen`. Only the newest unseen entry shows. Unset `lastSeen` counts as older than everything (a folder from before the feature); a fresh folder never qualifies because main records the running version at its first start. A start with the recovery prompt or the setup guide up is left alone; the card comes back next start.
- Every way out (the X, Escape, the backdrop) writes `whatsNew.lastSeen` = the running version and closes, even when the write fails. With `whatsNew.enabled` off the host never opens the card and only records the running version as seen, so turning it on later never resurfaces old notes. Settings › Updates › "Show" opens the newest entry at or below the running version regardless (`openWhatsNew`).
- A modal dialog at `z-40` like the guide, named by `#whats-new-title`. The title, the date and the X stay at the top; only the list scrolls, it takes the focus on open so the keyboard scrolls it, a wheel anywhere in the window scrolls it (a `wheel` listener on `window` forwards to the list unless the pointer is over the list, where the browser scrolls natively), and its scrollbar thumb stays visible (`sb-always`). The list reserves its scrollbar gutter permanently (`scrollbar-gutter: stable`, folded into the right padding): the image scales to the list's width, so a gutter that came and went would change the content height, and in the band where the two heights disagree Chromium keeps the scrollbar with nothing to scroll. The date is formatted from its parts as a local date, so it never shifts with the time zone.

## Views

- **Library** (`views/LibraryView.tsx`): a header with the flash, "Fetching artwork (n)" and Rescan, then a toolbar with search, Filter and Sort. Below it, the Recent strip (hidden while searching or filtering), the `GameCard` poster grid, and `CardMenu` for artwork actions.
- **Accounts** (`views/AccountsView.tsx`): grouped by launcher and ordered by `sortAccounts`: accounts used from One Launch first, then by name. The launch dialog reuses this order.
- **Account detail** (`views/AccountDetailView.tsx`): only the create form autofocuses. Ctrl+S sends the changed fields only; the header button always reads "Save changes" (disabled when nothing changed) so it is never mistaken for a step. A Create account from the Accounts page lands here with `created` on the route, which flashes what to do next once. Also holds the password panel, "Switch to this account", `SessionPanel` (Epic, Battle.net, Riot), a collapsed Advanced section, and a two-step delete.
- **Saved sign-in** (`components/SessionPanel.tsx`): one-line description ("Saved the first time you play on this account, and put back whenever you switch to it."); "Save sign-in" is the by-hand way, disabled with a tooltip saying why while the launcher holds no sign-in. No instructions here: the create form's Details panel carries the one first-Play line per launcher (`FIRST_PLAY`, naming the box to tick), and the hand-over checklist repeats it at the moment it matters. The "signed in as" row says "An account not yet linked in One Launch" (muted, with "press Save sign-in") for a sign-in nobody owns, never a warning. A Riot `lastSignIn` failure that names “Stay signed in” shows in the "Last sign-in" row. The "Saved sign-in" row is two lines whenever a sign-in is saved (last used for a switch, or not used yet) and holds that line open with a blank while the session loads (`account.hasSession` is known before `sessions:get` answers), so the panel never jumps when the hint arrives.
- **Settings** (`views/SettingsView.tsx`): five tabs pinned under the title (`TabList` in `PageHeader`'s toolbar). General holds the General panel (Start with Windows, tray, the setup guide's "Show again") and Updates (with both What's New rows); Launchers holds the launcher status rows and the Play panel (Steam automatic sign-in, Start Riot games for you); Artwork and Backups hold their panels; Advanced holds Launching (Preview mode, the Epic and Battle.net launch forms), Encryption and Diagnostics (log level, runtime, startup, data folder), then the Developer panel in dev builds. Only the chosen tab's panels are mounted, so their polls stop off-tab, and a tab change scrolls the page back to the top. The renderer never sends a launcher path: Locate… opens main's file dialog. A `settings:set` that succeeds bumps `settingsRevision`, which the view re-reads; one that fails shows "Could not save the setting: <message>" under its row and reloads, so the control snaps back.

## Copy conventions

- User-facing names hide internals. `dryRun` is **Preview mode** (off by default; check `=== 'true'`). The vault is **Encryption**. A captured session is a **saved sign-in**. A switch plan is a **Switch preview**. Never show UnifiedAuth, fingerprints, "capture", adapter ids or raw setting keys.
- Write plain second-person sentences with no jargon. A hint is one sentence. UI paths use `›`, as in "Settings › Backups".
- Errors: "Could not <verb> <thing>: <message>" (`text-danger`, `role="alert"` when it appears on its own). A failed job says what state it left behind: put back, needs a manual restore from Settings › Backups, or nothing changed yet.
- Hand-over to the user (2FA, expired session) is calm and explicit, never a failure: the warning-toned `AttentionPanel` with the adapter's title, its one-sentence `message` (why), its `steps` as a numbered list (what to do in the launcher window; whatever the adapter quotes in “ ”, the launcher's checkbox or button, is set in bold so the one thing to tick stands out), Copy login, Copy password (only if `canCopyPassword`), and Stop waiting. The panel is the one place that says the switch is waiting: the footer stays empty, the phase list drops the running step's title, and there is no countdown (the timeout outcome names the minutes afterwards).
- Strings that claim behaviour (clipboard, what is sent, what delete removes) must match main. Check the service before rewording one.

## Clipboard

- The renderer never receives a secret. Copy calls `accounts:copy { id, field }`. Main decrypts, copies and clears later.
- The flash must read "<Login|Password> copied · clipboard clears in <n>s while One Launch is open". Add " · Windows clipboard history may keep it" for a password when `historyExcluded` is false. `n` comes from `clearAfterMs` in the response. Never hardcode it.

## Accessibility conventions

- Dialogs: `role="dialog"`/`"alertdialog"`, `aria-modal`, `aria-labelledby`, `useFocusTrap` (keeps the focus React's `autoFocus` placed, else focuses the first control; restores focus on close). Put `autoFocus` on the primary action. When that action is disabled until data arrives, `useFocusWhenReady` moves the focus to it once it is enabled (LaunchDialog, ImportAccountsDialog).
- Transient messages use `useFlash` in an **always-mounted** `role="status"` span with `flashClassOf(flash)` (`sr-only` when empty). A live region mounted together with its text isn't announced. The launch dialog speaks through one `sr-only` status line (`jobAnnouncement`), not the repainting phase list.
- Popups (`Dropdown`, `MenuButton`, `CardMenu`) handle arrows, Home, End, Enter, Space, Escape and Tab, return focus to the opener, and are clamped/flipped to the viewport. Never hide a popup with `visibility: hidden` while positioning it: that blocks focus.
- Tabs (`TabList` over a `TabPanel`): `role="tablist"` of text-only `role="tab"` buttons with a roving tabindex; the arrows wrap, Home and End jump, and selection follows the focus. No `aria-label` on a tab: the drive scripts click them by their text.
- `Toggle` is `role="switch"` with `aria-label`. Icon-only buttons need `aria-label`. Tooltips go in `title` and include the shortcut if there is one.

## Gotchas

- Preview mode: Settings and Sidebar read it as off while settings load. The artwork and tray switches read `!== 'false'` (on unless stored off) and are disabled until settings arrive.
- `useIpcQuery` deps are spread into an effect with `exhaustive-deps` disabled. Pass primitive deps, not fresh objects.
- `LaunchDialog`'s `candidates` is a new array every render. Don't add effects that depend on it without care.
- Jobs live in main, which is why `ErrorBoundary`'s "a running switch continues" is true. Keep job logic out of the renderer.
