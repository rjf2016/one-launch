# Riot Client adapter

Code: `src/main/launchers/riot/` (`adapter.ts` = `RiotAdapter`; `session.ts` the session file; `client-log.ts` the client's log; `products.ts` the product table and metadata parsers). Tests: `test/riot-*.test.ts`, fixtures `test/fixtures/riot/`; the fake client is `src/main/launchers/sim/riot.ts`. Generic switch flow, backups, recovery: `../switching.md`. The switch (both ways) and a launch with the press have been run by the user on the real client, build 140 (`../roadmap.md`, R12).

The Riot Client signs in from one plain-text file, `RiotGamesPrivateSettings.yaml`. The switch is Epic's shape: store each account's copy of that file, put it back while the client is closed, restart the client, confirm the sign-in from the log and the account id the file names. A game is handed to the client the way its own shortcut does it; on build 140 that opens the game's page and waits for the user's Play, because Riot turned auto-launch off. Riot's anti-cheat (Vanguard) and account enforcement are strict and Riot approves no third-party tool, so the goal is to look, to Riot, exactly like the user restarting the genuine client on their own PC.

Client build 140 unless a build is named. Paths in Riot's files use forward slashes; always `normalizeLauncherPath`.

## Rules

These are not traded for convenience (`../roadmap.md` › standing decisions).

1. **Game processes and Vanguard are off limits.** No handle, path query, signal, or kill for a Riot game or for `vgc`, `vgk`, `vgtray`. `isRunning`, `runningGame` and the launch confirmation use image names only, from a listing that opens no process: not `tasklist`, which makes Windows ask every process for memory-read access (Processes). A forced kill of the client passes `tree: false`: the game is the client's child. The platform's `isRunning`, `listProcesses()`, close, and kill work this way for every launcher (`../development.md` › Platform helpers).
2. **No switch while a Riot game runs.** Refuse and ask the user to close the game. There is no "close it for me": closing the client mid-match is a leave, with queue penalties.
3. **No memory access, injection, hooks, overlays, drivers, or elevation.**
4. **No traffic to Riot's servers.** Never call them; an expired session hands over to a manual sign-in and is never refreshed in the background. The client's local server is used for one thing: the launch request its own Play button sends (`POST /product-launcher/v1/products/<product>/patchlines/<patchline>`), from `launchGame` alone, after the client has opened the game's page, to `127.0.0.1` on the port in `Config\lockfile`. The lockfile is read for that call and nothing else; its per-run password is used once and never stored or logged. No other endpoint (Launch).
5. **No credential automation.** Never pass, type, or paste a password into the client. Copy to clipboard for the user stays.
6. **One launcher file is written:** `RiotGamesPrivateSettings.yaml`, while the client is closed, after a snapshot, only in `runSwitch` and `applyRestore`. Never the install folders, `%ProgramData%\Riot Games`, `machine.cfg`, `RiotClientSettings.yaml`, or anything of Vanguard's.
7. **Keep the device identity.** `rso-authenticator.tdid` is Riot's "remember this device" marker. Never delete the file or the data folder, and never create the file (the client writes it at its first start). The signed-out state is the client's own: `psl.authorization.riot-client: null`, nothing else touched. Tools that wipe the device marker get an email verification on every switch.
8. **Never present an old token.** The client swaps the refresh token for a new one at every start and rewrites the file within seconds, so a stored copy is out of date as soon as the client has started from it. Before every overwrite of the file, a rollback included, store the session on disk for the account it belongs to. Write only the newest stored copy.
9. **Sessions never leave the PC.** No export or import of Riot sessions.
10. **Start the client the way its own shortcut does:** `RiotClientServices.exe` with no arguments for a plain switch, with `--launch-product` and `--launch-patchline` for a game: at the start of a switch that a launch follows, or handed to the running client. The arguments count only at the client's start.
11. The file is a bearer credential: vault-encrypted in `launcher_sessions` and in backups (`sensitive: true`), decrypted only at the moment of the write, never logged. Plans and UI show a fingerprint.
12. No notice or opt-in copy, and no claim of Riot's approval (`../roadmap.md` › standing decisions).

## Detection (`detectInstall`)

First hit wins; each candidate must contain `RiotClientServices.exe`:

1. The folder chosen with Locate in Settings (`riot.path`). Source `user`. If the exe is gone, the ladder continues and health shows a `chosen-folder` warning.
2. `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Riot Game Riot_Client.` › `InstallLocation` (HKCU, and the key name ends in a dot; the value ends in a slash).
3. `%ProgramData%\Riot Games\RiotClientInstalls.json` › `rc_default`, then `rc_live`: the full path of `RiotClientServices.exe` (other tools also read `rc_beta`). `associated_client` maps each game folder to its client exe. The install is often not at the default folder.
4. `HKLM` then `HKCU` `SOFTWARE\Classes\riotclient\shell\open\command`: `"<dir>\RiotClientServices.exe" --app-command="%1"`, first quoted token.
5. `C:\Riot Games\Riot Client`.

`installFromExe` (Locate) accepts only `RiotClientServices.exe`. The client's data folder is per Windows user, `%LOCALAPPDATA%\Riot Games\Riot Client` (also listed in `%ProgramData%\Riot Games\Metadata\Riot Client\Riot Client.settings.yaml` › `user_data_paths`); a chosen folder changes only where the exe starts from.

## Library (`listInstalledGames`)

- One product per `%ProgramData%\Riot Games\Metadata\<product>.<patchline>\` folder. Product ids: `valorant`, `league_of_legends`, `teamfighttactics`, `bacon` (Legends of Runeterra), `lion` (2XKO). Patchlines: `live`, `pbe`. `Riot Client` and `<product>.<patchline>.game_patch` folders are not products, and a folder can hold only a lockfile and a preview manifest (never installed).
- `<product>.<patchline>.product_settings.yaml` holds `product_install_full_path` and `product_install_root`, but **also exists for products that are not installed**. A product counts as installed when `<product>.<patchline>.ok` exists and the install folder does. Also seen for an installed product: `HKCU\...\Uninstall\Riot Game <product>.<patchline>` with `DisplayName`, `InstallLocation` and `DisplayIcon`. The Uninstall key's `DisplayName` names it, else the built-in table (`products.ts`), with the patchline appended when it is not `live`.
- `launcherGameId = <product>.<patchline>`, the metadata folder name, which the launch arguments are built from.
- Last played: `Config\RiotClientSettings.yaml` › `install.last-session-timestamp.<product>.<patchline>` (Unix seconds). Only that block is read.
- `needsUpdate`: the newest run log's last patch state for the product says `OutOfDate` (or, on build 116, `launchable: 0`): the client's Play button reads Update and a launch request only opens the product's page. The client logs every product's patch state at each start and again when it changes, so the newest run's last word stands until the next run. `<product>.<patchline>.update-status.json` (`updateAvailable`, `updateRequired`) is not read: it was stale after a real update.
- League and Teamfight Tactics name each other in `product_dependency` and share an install.
- Game processes, by image name only: VALORANT `VALORANT.exe` and `VALORANT-Win64-Shipping.exe` (seen); League and Teamfight Tactics share `LeagueClient.exe`, `LeagueClientUx.exe`, `LeagueClientUxRender.exe` and `League of Legends.exe`; Legends of Runeterra `LoR.exe`; 2XKO `2XKO.exe` / `2XKO-Win64-Shipping.exe` (unverified: no install to check). `runningGame` reports the first product with one of its images running.

## Session file (observed)

- `%LOCALAPPDATA%\Riot Games\Riot Client\Data\RiotGamesPrivateSettings.yaml`. Plain YAML, 4-space indent, not encrypted. Build 69 named it `RiotClientPrivateSettings.yaml`.
- Three top-level keys on build 140, each a nested map (`psl:` › `authorization:` › `riot-client:`; `riot-login:` › `persist:`; `rso-authenticator:` › `tdid:`), 4-space indent, CRLF, no BOM; list items sit at their key's indent. The shape changed between builds 116 and 140, so expect it to change again.
  - **`psl.authorization.riot-client` is the live session.** Signed in: `id_token`, `refresh_token`, `refresh_token_write_count`, `refresh_tokens_session_id`, `is_dpop_bound` (false), token times, `scopes`, `claims`. Signed out: `riot-client: null`, and nothing else in the file changes. A true `is_dpop_bound` would bind tokens to a device key: health warns.
  - **`riot-login.persist` is a leftover from builds up to 116.** It still holds `region`, `scopes`, and `session.cookies[]` (`tdid`, `ssid`, `sub`, `csid`, `clid`), but build 140 does not update it: after several sign-ins and sign-outs its cookies still carried issue times over a year old. Its `sub` is the account of that old sign-in, so **never use it for identity**.
  - `rso-authenticator.tdid`: the device cookie the client uses now (a signed token holding a device id, a nonce, and an issue time), with `expiryTime`. Rewritten many times per run and kept across a sign-out.
- Every start from a saved session rotates the tokens: `refresh_token_write_count` goes up by one, the `id_token` changes, and the file is rewritten about 2 s after start. `max_duration_between_restores` appears after the first such start (a number that matched the milliseconds since the previous token write).
- A copy holding an older `rso-authenticator.tdid` than the one on disk was accepted twice with no verification prompt, so the whole file can be swapped. Confirmed by hand with two accounts: putting an account's saved copy of the whole file back signs the client in as that account about 2 s after start, with no prompt; putting back the file a signed-out client wrote gives the login page. No other file was involved.
- **The client's own Sign out ends the session on Riot's side.** Every saved copy of it is refused afterwards (`invalid_grant`). One Launch never uses or needs Sign out, and its copy tells users to switch through One Launch instead.
- **Without "Stay signed in" nothing is kept.** After such a sign-in the client writes `riot-client: null` at exit, and the next start shows the login page. A closed client with `null` therefore means "no saved session": tell the user to tick the box. The switch cannot tell at the time (the file holds the session while the client runs, and `recapture` stores it), so the hand-over checklist makes the box its own step, and `sessionState` names it afterwards (Session reader and capture).
- A copy one start and eleven minutes out of date was still accepted, so an old token is not refused at once. How long that lasts is unknown (open question 2); rule 8 stands.
- **Identity comes from the `id_token`** (a JWT; the payload is the middle, base64url part). Its `sub` is the account id: UUID-shaped, the same across token rotations for one account, different between accounts. Other fields: `acct{game_name, tag_line, state}` (the Riot ID, a name: never logged), `country`, `country_at`, `login_country`, `lol_region`, `player_locale`, `amr`, `acr`, `iss`, `aud`, `age`, `phone_number_verified`, `account_verified`, `iat`, `exp`. The token is read for these fields only; its signature is not checked and it is never sent anywhere.
- Written at every sign-in, sign-out, and token change while the client runs, and in some runs once more at exit with no log line. Read it only after the client has closed. A user can sign out and in as another account without restarting the client.
- Builds up to 116 kept the session in the `riot-login` cookies, and a signed-out client kept only `tdid` there (build 109 log: `Persisting 1 RSO auth cookies: tdid`).
- Not session state: `Data\Sessions\` (empty), `Data\ShutdownData.yaml` (exit metrics), `Config\RiotClientSettings.yaml` (region, locale, an install identifier, `last-session-timestamp` per product, per-account UI flags under 64-character hashed keys). `Data\Cookies\Cookies` (SQLite) is written by the client window in some runs; sign-in does not depend on it (untouched through three account swaps).
- A session saved and left unused for four months was rejected. Community documentation says one to three weeks idle.

## Session reader and capture (`session.ts`)

- `readSession` reads only the `riot-client` block (its direct scalars) and fails closed: anything but `riot-client: null` or a block with an `id_token` naming a UUID `sub` and a `refresh_token` is `unexpected`, which the adapter turns into a `LAUNCHER_FILE` error (shown in the panel, a warning in health), never into "nobody is signed in". No YAML library: the reader understands the space-indented maps, one-line scalars and list items the client writes, nothing more.
- Identity is the id token's `sub`; the Riot ID (`acct`) is only a display-name suggestion (`listRememberedAccounts` › `personaName` when no account holds the id) and is registered with the log's redaction as soon as it is read. The fingerprint is the SHA-256 of the refresh token, so it changes at every client start; a session the fingerprint does not match is attributed by the account id instead.
- The stored blob is the whole file (`{ v: 1, file }`), which keeps both write strategies open: the confirmed whole-file swap and splicing the block into the current file (`spliceSessionBlock`, `planSignOut`).
- `captureSession` refuses while the client runs (its file says nothing about what the next start will find until it has exited) and when the file is `null` ("Stay signed in" was not ticked), and otherwise follows Epic: the owner by stored fingerprint, then by the account id; a linked id that differs is a refusal; the id is linked before the blob is stored (`storeSession`), so nothing is stored under an id another account holds. `listRememberedAccounts` lists the one account the file names and nothing else; it is never an import source (no login in the file).
- `sessionState.lastSignIn` is the newest log's verdict: `ok` for a sign-in, `{ ok: false, reason }` for a refused saved session or a sign-out, null while the client is still working or when it started with no saved sign-in (that is not an attempt, so the panel shows nothing). One more failure: a closed client whose newest run signed in by hand (`how: manual`) while the file holds `null` kept nothing, so the reason names “Stay signed in” and the account page explains its disabled Save.

## Log (`client-log.ts`)

`%LOCALAPPDATA%\Riot Games\Riot Client\Logs\Riot Client Logs\<local time>_<pid>_Riot Client.log`, one per run. Line 1 `Logging started at <local ISO time>`, line 2 `Application Version: <build>`; every later line is `<seconds since start>| <LEVEL>| <component>: <text>`. The reader takes the newest run by name (the name is the run's local start time) the way the Epic and Battle.net readers do: `logMark` / `eventsSince` for "what was appended since" (the whole new file when a new run began), `currentRunEvents` for the whole run, at most the last 8 MB. The parser returns only fields a strict pattern matched (a state name, a product id, a status word, an error code) and never a raw line: **telemetry lines, which embed cookie and token values, are skipped**, as is any line over `MAX_LOG_LINE_LENGTH`. Events the client repeats back to back (a state, the device cookie written again) count once. **The log never names the account**: identity comes from the session file, the log gives only the verdict.

- `lastSignIn(events)`: the last verdict, or null. On build 140 the end states decide: `PendingProductContext` is signed in (`how`: `restored` after a `RestoreAuthorization`, `manual` after `LoginTokenExchange`), `PendingLoginStrategy` is the login page, and the lines of the same attempt (back to the previous `PendingInitialization`) say why: `rejected` after the `invalid_grant` error, `error` after another `rso-auth` error or a restore with no verdict, `signed-out` after a deleted authorization or `PendingCreateAuthorization`, else `no-session`. Only `rejected` may mark a stored session stale. Builds up to 116 are read from their `riot-login` lines.
- `startupFinished(events)`: a verdict or the terms page (`PendingEulaAcceptance`) is logged, so a restarted client can be closed again. `exitedCleanly(events)`: the lock-file removal is logged.
- **A second `RiotClientServices.exe` while the client runs** (a game shortcut, or One Launch's launch before it learnt better) writes its own small log (`ProcessSingleton: Did not initially acquire process singleton`, `Message to other Riot Client succeeded`, `Did not acquire process singleton`) and exits. That file is newer by name than the run's, so `newestClientLog` skips a log of at most 64 KB that holds `Did not acquire process singleton`; otherwise every reader would take the stub for the current run.
- A start with no saved sign-in on build 140.0.7: `PendingInitialization`, `PendingClientId`, the file written, `PendingLoginStrategy` (no `PendingPersistenceInitialization`); the restore of a saved sign-in: `PendingInitialization`, `PendingClientId`, `RestoreAuthorization`, `PendingEulaData`, `PendingPersistentFlagsData`, `PendingProductContext` in about 3 s. The parser's attempt window (back to `PendingInitialization`) covers both.

- Launch request handed to a running client (build 140.0.7, seen twice on the user's real switch; the same on 140.0.8): the running core logs `Setting product context to <product>.<patchline>, willAutoLaunch=false` at once, the pipeline (`SelfUpdate`, `LifecycleSync`, `LeagueRegion`, `Login`, `HomeBaseCountry`, `Eula`, `ClientConfig`, `VanguardHealthCheckStatus`, `PatchlineData`, `RiotIdRequired`, `AccountAlias`, `LeagueRegionElection`, `PlayerAffinitySync`, `AppRepairAndUpdate`, `PatchStatus`, `AgeRestriction`, `Permissions`, `LaunchRestriction`, `PatchlineLaunchDisabled`, `VngAccountRequired`, `RestartRequired`, `WaitForLaunch`, about 13 s with the patch check), and **`riot-client-lifecycle: Client is already running. The transitions and the refusals name no product, so all three count them only while the product's own lines are the latest to name one: another product chosen in the client meanwhile takes what follows.
- Start with the arguments (build 140.0.8, seen three times on the user's real launches): `Setting product context to <product>.<patchline>, willAutoLaunch=true`, the feature flags (`autoLaunch.disabled` true), then at once `willAutoLaunch=false`; the sign-in `PendingInitialization`, `PendingClientId`, `RestoreAuthorization`, `PendingProductContextInitialization` (this state, not `PendingProductContext`, when a product context is set; `lastSignIn` takes both as signed in); the pipeline to `WaitForLaunch` in about 2 s; and **`riot-client-lifecycle: Attempting to launch default product with reason (Auto-launch is disabled)`**: the page is up, nothing starts. - Clean exit: `riot-client-lifecycle: Attempting to quit` (a tray Exit) and `Attempting to quit. SwitchToBackgroundMode: False` (also after a core-only close), then `ProcessSingleton: Removal of LockFile complete`.

## Switch (`buildSwitchPlan`, `runSwitch`)

Steps: `close`, `capture`, `backup`, `file`, `start`, `wait`, `verify`, `manual`, `recapture`. `preflight`, `switchAccount` and `restoreBackup` follow `../switching.md`, with these Riot particulars:

- **A running Riot game refuses the switch and the restore** with `GAME_RUNNING` (`GameRunningError`, a refusal code: the user closes the game, there is no "close it for me"). The dry-run plan carries the same sentence as a warning. The check is `findRunningGame()`, image names only, and a process listing that fails refuses as well: only the status's `runningGame()` reads a failed listing as no game.
- **Who is signed in.** The file names the account (the id token's `sub`) whether the client runs or not, since the client writes it at every sign-in and sign-out. An account is *in place* when the file names it; *already active* when the client is running, the file names it, and the newest run log reports a sign-in. After the log's verdict the switch reads the file for the account id: a mismatch with the account's id (or an id another account holds, for an account with none) is `wrong-account`, which fails the switch and rolls back; an id nobody holds is adopted (`linkIfNew`).
- **Strategy** `remembered` when in place or a non-stale saved copy exists, else `credentials` (the sign-out path, then one manual sign-in).
- **Writes.** The saved-copy path writes the account's stored file whole (the swap confirmed by hand: sign-in, write count and device cookie together). The sign-out path (no usable saved copy) splices `riot-client: null`, the client's own signed-out state, and changes nothing else (`planSignOut`). The file is never created: without it the plan is not executable and the user starts the client once by hand (rule 7).
- **Before every overwrite, the rollback and `restoreBackup` included, the sign-in the file holds goes to its owner** (`storeOnDiskSession`, best effort; rule 8). Owner is by stored fingerprint, then by the account id the file names; a sign-in nobody owns is left alone, and the snapshot that replaces it is pinned (`UNOWNED_SESSION_PIN`).
- Order: refuse while a game runs → close (confirmed) → stop if the client is running again (something else started it; nothing written) → `saveOutgoing` → snapshot (`Data/RiotGamesPrivateSettings.yaml`, vault-encrypted) → write → fail and roll back if the client is running now → start the exe, with the game's launch arguments when a launch follows (`SwitchOptions.game`; the result's `startedWithGame` names it and `readyAt` stays null, nothing being sent afterwards), else with no arguments and a `readyAt` 2 s later that only a game launch waits for → confirm. A rollback closes the client first (no signal), stores what the file holds for its owner, then restores the one file.
- **Verdicts.** `PendingProductContext` in the new run log is a sign-in (remembered waits 45 s; credentials polls once); the login page hands over to the user (`manual` step, up to 10 min) with a checklist: enter the login and password, tick “Stay signed in” before signing in (or the client forgets the account when it closes), press Sign in. The "switch through One Launch rather than the client's Sign out" advice lives on the account page's Saved sign-in panel. Only `invalid_grant` (`rejected`) marks the stored copy stale; a service failure or a sign-out does not. During the manual wait a sign-out is not final. A timeout gives `needsSignIn` with the client left on its login page; a cancel after the client started does not roll back.
- **Recapture.** After a manual sign-in the file is stored once the client has written a sign-in that differs from what the switch left there (up to 15 s), and only when it names the account's id. The saved-copy path marks the stored copy verified instead; the rotated file is captured at the next overwrite.
- `restoreBackup` refuses while the client runs (`LAUNCHER_RUNNING`; the user exits it from the tray icon) and while a game runs, and takes a "Before restoring" snapshot first (pinned when the state it replaces is a sign-in nobody owns).

## Shutdown

`shutdown()` touches only the client's own processes, by image name (rule 1), in the two steps observed by hand: a window close for the core, `RiotClientServices.exe`, and a wait of up to 3 s for every such process to be gone (its one window, the tray icon's `TrayIconClass`, swallows the close on the current build, so the forced close normally follows); then, since the core leaves the window processes behind, a window close for `Riot Client.exe` (the processes with a window get it, the windowless helpers get nothing and exit with their parent) and a wait of up to 10 s. A forced close follows only a polite one that was ignored, and never takes the tree: a running game is the core's child. Then the restart watch: 5 s, cut to 1.5 s the moment the log gains the lock-file removal (a clean exit), whenever that line lands, and from the start after a forced close; a core that comes back is given up to 45 s to reach a sign-in verdict in its new log (`startupFinished`) and is closed again, three rounds at most. Window processes left behind with no core are closed the same way. An aborted signal ends any wait with `SwitchAbortedError`. The platform's image-name check allows the single space in `Riot Client.exe` (`../development.md` › Platform helpers).

### Processes (observed)

- `RiotClientServices.exe` (core, one process), `RiotClientElectron\Riot Client.exe` (window, several processes; older builds `UX\RiotClientUx.exe`), `RiotClientCrashHandler.exe`. `vgtray.exe` and the `vgc` service run whether or not the client does.
- `Config\lockfile` exists only while the client runs. Its presence is a running signal; its content is never read (rule 4).
- **`tasklist` and `taskkill /IM` are not quiet.** Both list processes through WMI (`SELECT ... FROM Win32_Process`, no path or command line), and for each run the WMI host (`WmiPrvSE.exe`, not the caller) opens every running process asking for `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` (traced: 235 of 235 processes, twice). A Riot game and Vanguard get that request whenever anything on the PC runs `tasklist`, so it is ordinary, but the adapter must not be the cause: no `tasklist`, `taskkill`, WMI, or `Get-Process` path for anything Riot. One Launch runs none of them: `WindowsProcessController` lists, closes, and kills without WMI. The two-step close was done by hand with `taskkill /IM`, which posts `WM_CLOSE` to one window per process, the topmost hidden one when none is visible (checked on a throwaway that logged every message it got); the platform's `close()` posts it to the visible window, else to every hidden top-level window. On the current build the core has one window of its own, `TrayIconClass`, and it swallows the message: no quit attempt in its log on any real switch, nor on a probe by hand, so the polite close no longer ends the core and the forced close follows the short wait (`../development.md` › Platform helpers).
- As first observed on build 140.0.7 (not on the current build, previous point), a polite close, no `/F` needed, in two steps: `taskkill /IM RiotClientServices.exe` (the core exits cleanly in about a second: lock file removed, `ShutdownData.yaml` written, log `Attempting to quit. ...: False` with no plain `Attempting to quit` line before it; **the window processes stay open** and the tray icon lingers until hovered, so the client still looks alive), then `taskkill /IM "Riot Client.exe"` (the window closes; the processes that own a window get the signal, the windowless helpers answer `ERROR: ... can only be terminated forcefully` and then exit with their parent). `close()` sends a process without a window nothing and reports no error for it; poll for the processes to go.
- Exit from the tray icon closes everything: log `Attempting to quit`, `Attempting to quit. ...: False`, `Removal of LockFile complete`.
- The client's shortcuts and uninstall strings use `RiotClientServices.exe --launch-product=<product> --launch-patchline=<patchline>`.

## Launch (`launchGame`)

- `"<installDir>\RiotClientServices.exe" --launch-product=<product> --launch-patchline=<patchline>`, started from the install folder (rule 10): handed to the running client (a singleton; the second process messages it and exits), or starting the client when it is closed. When the switch just started the client with these arguments (`startedBySwitch`, from the result's `startedWithGame`) and the run's log shows the product context, nothing is sent and the run's own log is watched from its start: the sign-in and the page come up together, so Play follows the confirmed sign-in in about 2 s instead of the 8 s of the grace plus the running client's pipeline. **Riot has turned auto-launch off on build 140** (its `autoLaunch.disabled` feature flag; seen on the user's real launches, both ways), so the client opens the game's page, brings its window forward, and waits for Play, exactly as the game's own shortcut does now. The launch therefore ends in a **hand-over**: once the page is up (`launchPageShown`) the result carries `handOff` ("Press Play in the Riot Client window to start <game>; it is open on the game's page."), `LaunchService` puts it on the job, and the dialog ends "Switched to <account>" with that sentence instead of "Launched as". Should a client start the game on its own again (build 77 did), the game's process name or the launch lines confirm it and the result reads "(the Riot Client started the game)". The client is never closed for a launch: that only costs a restart and changes nothing. The id must parse as `<product>.<patchline>`; anything else throws before the install is looked up.
- Refused before anything is touched, with refusal codes (WARN), so the job fails with the switch kept ("only the game launch failed"): a Riot game running (`GAME_RUNNING`: "<game> is already running." for the same product, "<game> is running. Close it, then press Play again: One Launch never closes a Riot game." for another), and a product the newest run log reports out of date (`GAME_NOT_PLAYABLE`: "<game> needs an update before it can start. Update it in the Riot Client window, then press Play again."). The launch dialog's picker says the same before the switch ("The Riot Client wants to update <game> first…"). The switch's own start still carries the game's arguments then, as the game's shortcut would, so the client opens on the game's page with its update waiting. A process listing that fails refuses as well, with its own error rather than a refusal code: the game check never fails open (`findRunningGame`).
- After the arguments are sent, up to 90 s (`launchConfirmMs`; seen: the page up about 13 s after a request to the running client, with the patch check, and about 4 s after a start), the log is watched for, in this order: an out-of-date patch state (fails with the update message), the game started (`gameStarted`, or the game's own process name: `gameImagesOf`, all of them in one listing at most once a second, `processPollMs`, while the log is read every poll), the page up (`launchPageShown`: the hand-over), or the login page (`lastSignIn` not ok, a closed client only: fails with "opened on its login page instead of signing in (<detail>) … Sign in there with “Stay signed in” ticked and press Play"; the saved copy is not marked stale here, the next switch decides that). Silence fails it, naming what happened: "did not start within 90 s" when the client set the product context (`launchAccepted`), "did not act on the launch" when it logged nothing (updating itself). A cancel during the watch returns "(stopped watching for the game start)".
- **Pressing Play for the user** (`riot.pressPlay`, on by default; Settings › General › "Start Riot games for you"). Once the page is up, `launchGame` sends the client's local server the launch request its own Play button sends (rule 4's one exception; `local-launch.ts`): `node:https` to `127.0.0.1` on the lockfile's port, basic auth `riot:<lockfile password>`, an empty body, 10 s, no proxy, no redirect, the answer's body dropped; only a lockfile named `Riot Client` with `https` and a usable port is accepted, and the product id is validated before the file is read. Then the log and the process list are watched up to 30 s (`playConfirmMs`; about 7 s seen from Play to `WaitForSessionExit`) for the game, the same way as above. Started: the result reads "(One Launch pressed Play and the Riot Client started the game)" and the dialog "Launched as". A request the client refused (a status, a connection error, no lockfile) or did not act on leaves the hand-over as it was, with what happened appended to the command for the log and Show details; the launch never fails because of this step. An out-of-date patch state logged meanwhile fails it with the update message, as before; a cancel ends it with "(stopped watching for the game start)". The real platform supplies the channel (`WindowsRiotLocalLaunch`); the fake one routes it to the simulator's `pressPlay` and records each request in the fake report (`riotLaunchRequests`), and the `pressPlayFails` knob makes the simulator refuse it.
- Why the page needs a press at all: Riot's own FAQ says that from 2026 "Riot Client will always be shown when you launch a game on PC, even if you are logged in and your game is up to date", that a shortcut "will now open that game's page in Riot Client first", and that "we know some players would prefer to launch directly into game"; a Riot employee confirmed it as an intentional test tied to the new League client. The client's flags: `autoLaunch.disabled` true, `direct_launch_opt_in.enabled` false, `restart_after_direct_launch.enabled` false, with `"enable_direct_launch": true` in its configuration dump, so an opt-in exists in the code and is not switched on. Should Riot switch it on, the arguments start the game again and the watch above confirms it before any press.

## Artwork (`gameIcon`)

Riot's games are not on Steam, so the lookup finds nothing. `gameIcon` names the product's own icon: `<product>.<patchline>.ico` beside its metadata first, else the Uninstall key's `DisplayIcon` when that is an `.ico` file (a trailing `,<index>` dropped; an exe is not taken). The artwork service reads it as the stand-in grid (`../artwork.md`). Seen: `valorant.live.ico` holds a 256 px PNG frame and four BMP frames, and `DisplayIcon` names that file with forward slashes.

## Health (`healthCheck(known?)`)

Reuses the status pass's install and running state when given. Rows: `install`, `chosen-folder`, `process`, `installs` (`RiotClientInstalls.json`: `rc_default` and the associated game folders), `products` (each metadata folder: installed, installed and needs an update, install folder missing, not installed), `data` (the session file without a value: absent, signed out, holds a sign-in for Riot account `…1234`; warns when device-bound or in an unknown shape), `log` (run count, the newest run's build and verdict; warns when the saved sign-in was refused), `sessions` (warns when any is stale), `backups`.

## The fake client (`sim/riot.ts`)

Encodes this model of build 140, in the `all-four` and `unowned` trees: it signs in from the file and rotates the token at every start, writes a run log with the PSL states above and a patch state per product, lands on the login page for `null`, an `invalid_grant` (`rejected` knob, after which it writes `null`) or an `authError`, lets a scripted user sign in by hand (`signInWhenAskedMs`, `signInAs`, `staySignedIn`, which decides whether the core's exit writes `null`), and refuses every copy of a sign-in `signOut()` ended. A start with the shortcut's launch arguments opens the game's page once signed in, as build 140 does: the product context with auto-launch and at once without, the patch state, build 140's pipeline, and `Attempting to launch default product with reason (Auto-launch is disabled)`; the same request handed to the running core sets the context without auto-launch and ends with `Client is already running. Explicitly request focus instead of launching (Auto-launch is disabled)`. `pressPlay(id)` stands in for the user's Play on that page: `Launch starting`, the game's first image name in both views of the process list, `WaitForSessionExit`. `directLaunch: true` models a client that still launches at its start, as build 77 did. A product in `updatesPending` only gets its page (`OutOfDate`, the real client's `is out of date, and needs patching before launch` line, and the refusal `Product is not up to date`), one the simulated install does not carry only its context, and a client on its login page does nothing with the request. `ensureProducts` lays down the metadata, the `.ok` marker, the install folder, `RiotClientInstalls.json` and a placeholder `.ico` per product; `defaultRegistry` the Uninstall keys with `DisplayIcon`. Its id tokens are unsigned placeholders whose `sub` is the account id; a scenario seeds an account's saved copy with a `refreshToken` alone. A real client can disagree with all of this, which is what the user's real switch (R12) is for.

## What Riot acts on

- Vanguard blocks tools that read game memory and has no allow list. Riot's third-party policy targets tools that affect game integrity or give an advantage; it does not mention account switchers.
- The Terms of Service forbid "unauthorized third party programs, including ... automation programs that interact with the Riot Services in any way". Broad enough to cover a switcher if Riot chose to; only an answer from Riot removes that.
- Alternate accounts are allowed when the player created and levelled them and never shares them. Shared, bought, and boosted accounts are suspended or banned, and a penalty on one account applies to every account Riot links to the same person. Riot support ships on by default with no notice; copy never claims Riot approval.

## Inspecting Riot files safely

- Print the session file as key structure with every value replaced by its length. Never extract, compare, or hash a value outside the adapter.
- When sampling a log: drop lines containing `telemetry`, `token`, or `cookies`, cut any JSON payload, and mask ids, emails, Riot IDs, and long runs before printing.
- Fixtures (`test/fixtures/riot/`): placeholders of the same shape and length for every cookie, token, and id; telemetry lines removed.

## Other tools

- TcNo, RiotAccManager, and V-Shift swap the same file; some also copy `Sessions\`, `RiotClientSettings.yaml`, and `client.config.yaml` from the install folder. Unverified whether those matter.
